# 0.11 NPC 日程与世界时间契约（M1 冻结）

开发基线为已正式发布的 `v0.10.0`，提交 `066b10eb285824ac480e1072cb10ab5660660573`；0.11 在独立分支 `codex/schedules-0110` 按 M1–M7 交付。M1 仅冻结契约和固定样本，**尚未实现 v4 校验、推进器或游戏入口**。不提前打标签或发布。

## 范围与版本

采用世界 **schema v4、rulesVersion 1**，在 v3 知识和任务契约上增加确定性的每日 NPC 移动。v1–v3 的严格读取、内容哈希和执行语义保持，读取旧聊天不自动升级。v4 的 `schedules`、`scheduleStates` 必填，允许空数组；v1–v3 不接受这些新字段。审计所有 `schemaVersion === 2/3` 分支，确保 v4 继续执行知识、任务和恢复后的活动过滤。

只通过现有 `world_command` 的 `advance_time` 推进；不增加日程工具或模型调用。查询、刷新、提示构建、作者预览、重启、导入、迁移和恢复均不推进时钟或执行日程。无自主规划、随机事件、离线推进、自动交易、秘密传播、任务期限或自动接取/推进/领奖。

## 模板与快照字段

模板新增：

```json
{
  "schedules": [{
    "id": "innkeeper_daily",
    "actorId": "innkeeper",
    "description": "仅作者可见的编排备注",
    "points": [
      {"minuteOfDay": 10, "locationId": "square"},
      {"minuteOfDay": 30, "locationId": "tavern"}
    ]
  }]
}
```

- 每世界 0–64 份日程，每 NPC 至多一份；每份 1–16 个时间点，不能给绑定玩家配置日程。
- `id` 使用现有实体 ID 规则（1–128 字符、无空白或控制字符），世界内唯一；`description` 可省略，最多 2000 字符，仅作者可见。
- `minuteOfDay` 为 0–1439 的整数，同一日程不得重复；允许输入未排序，执行顺序不依赖数组顺序。`actorId`、`locationId` 必须有效；不接受未知字段、分数、负数或超限值。
- 不配置日期、时区、夏令时、持续时间或旅行耗时。到点直接改变 NPC 位置，不改变其 alive/dead/inactive 状态。初始位置仍来自既有初始状态，不由日程反推。

快照新增一份与模板日程逐一对应的进度：

```json
{
  "scheduleStates": [{
    "scheduleId": "innkeeper_daily",
    "activatedAt": 0,
    "processedThrough": 9
  }]
}
```

字段含义与校验：

| 字段 | 约束 |
| --- | --- |
| `scheduleId` | 恰好对应一份模板日程；不允许缺项、重复或悬空项 |
| `activatedAt` | 在此恢复点启用日程的累计分钟；新聊天为 0，迁移新增日程为该恢复点当前分钟 |
| `processedThrough` | 已处理到的累计分钟，必须等于快照 `clockMinutes`，且不小于 `activatedAt` |
| `lastOccurrenceAt`（可省略） | `(activatedAt, processedThrough]` 内最后一个已消费触发点的绝对分钟；存在触发点时必填且精确匹配，不存在时必须省略 |

所有分钟均为整数，沿用时钟上限 **525600000**。`activatedAt` 不随普通推进改变；每次成功推进更新全部日程的 `processedThrough`，包括本次没有触发点的日程。`lastOccurrenceAt` 包含死亡、停用和已经在目的地的跳过点；不从事件列表推导或修补进度。非法进度按损坏恢复点处理，不自动补跑。

## 时间区间、排序与预算

数学日序 `dayIndex = floor(clockMinutes / 1440)`，触发点绝对分钟 `dayIndex * 1440 + minuteOfDay`。样本的“第 0 天”为累计分钟 0–1439；玩家界面沿用现有从“第 1 天”开始的显示，`displayDay = dayIndex + 1`，避免改动旧聊天的日期显示。

给定旧时间 `t0` 和正整数增量，先校验新时间 `t1` 未超过时钟上限，处理区间固定为 **`(t0, t1]`**：

1. 恰好到达时间点执行；旧时间恰在时间点时不再执行该点。0 分钟、负数、分数仍拒绝。
2. 日程每日重复；`minuteOfDay=0` 在新建世界的分钟 0 不执行，首次为分钟 1440。显式迁移在时间点启用同样不执行当刻。
3. 预先计算所有落在区间内的触发点，按 **绝对分钟升序，再按日程 ID 的 UTF-16 码元字典序升序** 排序；不使用依赖语言环境的排序。单日同日程时间不重复，排序不存在其他平局。
4. 每次命令最多消费 **256** 个点，包括死亡、inactive 和已在目的地的跳过点。257 个即在修改任何状态前拒绝；不先处理 256 个，不靠裁剪事件掩盖遗漏。
5. 预算按整个区间计算，不逐分钟扫描长时间跨度。超过预算使用 `SCHEDULE_LIMIT`，玩家错误说明为“本次时间推进超过日程处理上限，请缩短等待时间”，不附日程 ID、未来时间或目的地；超过时钟上限沿用 `TIME_LIMIT`。

将大段等待拆成多次合法命令是允许的，每次仍需整轮成功提交。预算限制不改变每日时间表，也不自动选择较短等待。

## 纯推进与事务

推进器输入已校验的模板、快照和目标分钟，输出新快照、完整的有序触发回执及任务视角变化证明；不得修改输入、读系统时间、访问文件、调用模型或执行其他工具。随机事件 ID、命令 ID 和回合标识由外层统一装配，不影响纯计算结果。

预检通过后在私有副本中依序处理每个点：

- NPC 为 `alive` 且不在目的地：移动到目的地。
- NPC 为 `dead` 或 `inactive`：跳过，不移动、不复活，仍消费该点。之后恢复 alive 只处理未来点。
- NPC 已在目的地：消费并记 `already_there`，不制造一次实际位移。
- 每个点后按现有规则重算玩家所在地的 `scene.presentActorIds`，稳定排序。**沿用现有语义：inactive 不在场，dead 可以在场，但不可交互**；日程跳过死亡 NPC 不改变这条规则。
- 在每个点后的中间状态重新观察任务玩家投影。把“曾出现不同任务视角”的证明累计到事务，不因 NPC 回到原处而清除。即使多个点位于同一 `advance_time` 内，也不能只观察命令结束时的快照。

任意引用、进度、上限或执行错误，整个命令拒绝，时钟、位置、在场列表、进度和事件全部不变。成功时所有日程消费完毕才设置最终时钟并暂存；后续工具立即使用新位置判断购买、交付、知识交互等。单条 `advance_time` 仍只增加一次世界 revision；事件数量不额外增加 revision。

单次命令回执保持既有 `advance_time` 主事件；新增内部事件 `schedule_move`、`schedule_skip`，携带 `scheduleId`、`actorId`、`fromLocationId`、`locationId`、实际触发的 `worldTimeMinutes` 及既有事件标识。skip 另带 `skipReason: dead|inactive|already_there`。日程事件先按触发顺序，主事件最后、时间为 `t1`。完整结果先用于预算、过滤和回执，再将快照 `recentEvents` 保留最后 100 条；进度和视角证明不随事件裁剪丢失。

整轮继续使用 WorldTransaction 和一次 JSONL 提交：单/双阶段、simple/bridge/takeover 共用规则。正文失败、停止、空输出、上下文超预算或 revision 冲突，撤销所有暂存时间、移动、交付、奖励和知识。取消信号贯穿全过程；重启标记未完成运行 interrupted，不继续推进。命令幂等和请求 ID 回执沿用现有契约，坏 JSONL 行跳过扫描且原文保留。

只重写正文不执行工具，不改变时间、进度、事件、位置或任务；重新生成从回合前检查点重新结算。一次跨两点与分两次推进应具有相同的**玩法状态**（时钟、角色、场景、金额、库存、知识、任务、日程进度）；命令数不同导致的 revision、事件 ID、命令回执和叙事标识不要求逐字一致，不能据此宣称整个 JSONL 相同。

## 玩家信息与缓存边界

玩家默认 HTTP、WS、工具、三模式提示、叙事包和活动诊断不接收完整模板、`schedules`、`scheduleStates`、作者备注、内部日程 ID 或未来目的地。玩家只接收当前公开硬状态和已经发生的可见移动（角色、实际起止地点、时间、服务端摘要）；skip 事件不进入玩家投影，移动事件去掉内部日程来源。发生过的公开位置仍沿用旧语义，不新增战争迷雾或 NPC 隐身。

作者通过独立入口查看完整规则和跳过记录；模拟预览使用副本，遵守同样区间与预算，不写聊天、不扣用量、不执行工具。JSONL 和备份保留完整模板/进度/事件，MD 仍只导出活动路径正文；不是多人权限系统，不承诺清除已经写入正文的内容。

投影之后才构建 0.7 的来源索引和缓存。缓存绑定活动路径、模板、当前状态（含时钟/位置/进度）、知识视角、任务视角及算法版本；切候选、编辑、恢复、迁移后重新选择，缓存缺失可重建。任务视角证明必须涵盖同命令及同回合的开放→关闭→开放、并行工具和阶段变化。混合视角活动保守隐藏上下文、阶段提示与工具参数/摘要；旧记录无完整证明时不放行，保留真实用量、状态与原始活动文件。

恢复至旧分支、v3/v2/v1 或无世界后，历史 v4 内容同样按当前有效视角过滤；不能因当前版本没有日程而跳过知识/任务授权。过滤必须发生在 HTTP 快照、分页活动、WS 同步、历史召回、诊断和后续模型请求等出口。玩家历史正文不作为知识或任务授权。

## 迁移与恢复

只允许显式 v1/v2/v3→v4 升级和保守的 v4 模板迁移，禁止降级。沿用已有升级规则：v1 新知识为空，低于 v3 的旧世界任务进度为空；不灌入新模板的初始知识或金额。读取旧存档不改版本、哈希或文件。

新日程按**各恢复点自己的当前时间**设置 `activatedAt = processedThrough = clockMinutes`，省略 `lastOccurrenceAt`；不执行过去或当刻的点，不根据未来时间表重摆 NPC。已有日程定义必须完全相同，进度原样保留；首版阻断修改、删除、改 ID（包括改绑定角色、点、目的地或作者备注），需要不同规则建立新世界。新增也须满足每 NPC 仅一份的约束。

迁移保持已有时钟、角色状态/位置、场景、余额、库存、知识和任务进度。不依靠最近 100 条事件，不伪造日程执行历史。全部活动世界、候选、检查点、原生 swipe 和隐藏 continuation 使用原始源表校验；任一源模板缺失、v4 进度非法或恢复点损坏，整份迁移阻断，不返回部分写入结果。预览不写文件，应用前备份并单次原子写入。

候选和检查点携带各自完整 `scheduleStates`；恢复是直接读取对应快照，不执行推进或补跑。叙事包保留原始来源，迁移后指纹不匹配禁用重写，不把旧包静默改成按新日程结算。分支切换、重启、JSONL 导入导出和备份恢复应重建相同玩法状态。
